# Foreground, host-authenticated confirmation for permanent deletion

Permanent deletion now stays owned by the Finder extension, reads a hardened fail-closed safety preference, and delegates the user decision to a foreground host-app modal. DNC repeatedly wakes the host with a durable request path; approval returns over a Unix-domain socket and is accepted only when `LOCAL_PEERPID` resolves to the containing host app's code hash. The prior direct DNC-forgery, startup-loss, and stale-modal findings are addressed, but shipping remains blocked by missing request-context binding, inconsistent lifetime enforcement, and an unbounded client connection path.

**Watch for:** **confirmed** same-user request substitution can downgrade the displayed count/type-to-confirm semantics without invalidating the authenticated reply; **confirmed** request intake expires at 60 seconds while the extension starts a fresh 120-second timer only after host launch; **confirmed** the reply client's pre-timeout blocking `connect()` can prevent the serialized host queue from advancing; **confirmed** tests do not cover these adversarial and deadline paths.

**Verdict**: NEEDS_CHANGES

## High-level view

DNC has no approval message: it supplies a path that wakes the host, and only the socket response can authorize the extension. The socket authenticates the responding executable, but its response carries only request ID and Boolean, so it does not prove that the host displayed the same paths, item count, and confirmation mode that the extension created.

The host modal derives its remaining life from `createdAt`, dismisses itself at expiry, and skips stale queued requests. The request reader nevertheless rejects work after 60 seconds, while the extension waits for host launch before starting its 120-second timeout; launch itself is outside any timeout.

The server uses a nonblocking listener and accepted socket, bounded polling, a 4 KiB cap, and invalidation checks; the TaskGroup timeout invalidates the server before cancellation. The client enables `SO_NOSIGPIPE` and bounds peer-closure waiting, but does not become nonblocking until after `connect()`, write, and half-close.

The dangerous-operation preference remains separate from menu configuration and resolves read or validation failures to confirmation. Bypassing the modal requires two valid reads of the same disabled revision, and deletion remains extension-owned with path, resolved path, device, and inode revalidation before removal.

<summary>Issues (4)</summary>

1. **Approval context can be substituted** — **confirmed:** a same-user process can replace the request data while preserving its ID/socket, and the authenticated response does not echo or bind the displayed paths/mode. Bind the response to a host-computed digest of the exact request presented, or transfer the request over authenticated bidirectional IPC.
2. **Confirmation lifetime has three clocks** — **confirmed:** request intake uses 60 seconds, host launch is unbounded, and the extension starts 120 seconds only after launch. Enforce one `createdAt + 120 seconds` deadline across intake, launch, modal, socket receive, and queue cleanup.
3. **Reply connection is unbounded** — **confirmed:** `connect()` runs on a blocking socket before the two-second peer-closure timeout applies, so backlog saturation can pin the serialized modal queue. Make connect/write/half-close/peer-close nonblocking under one deadline.
4. **Boundary regressions are untested** — **confirmed:** the passing suite covers basic hash acceptance and file validation but not context substitution, delayed launch, backlog saturation, absolute expiry, or queue progress. Add deterministic socket/deadline tests and a host-extension context-binding integration test.

<summary>Details</summary>

### Host authentication is not bound to the confirmation context

**confirmed:** the extension authenticates `LOCAL_PEERPID` against the containing app's code hash before checking the request ID (`FinderExtension/FeatureServices.swift:156-175`), and the client remains connected until server closure. The trust gap is that DNC chooses the request-file path (`Shared/MenuAction.swift:1153-1173`), the host derives displayed count and type-to-confirm mode from that file (`App/SuperRightClickApp.swift:135-146`), but the authenticated response contains only `requestID` and `approved` (`Shared/MenuAction.swift:961-964`, `App/SuperRightClickApp.swift:102-110`). The server compares only the ID before returning the Boolean (`FinderExtension/FeatureServices.swift:168-175`).

Secure-file checks reject symlinks, hard links, permissive modes, and mutation during a read, but ownership and `0600`/`0700` permissions identify a user, not a process (`Shared/MenuAction.swift:708-725`, `Shared/MenuAction.swift:857-870`). Another unsandboxed process under the same user can replace a pending request with a stable valid file carrying the same ID/socket but one decoy path and `.standard` mode. If it wins the host-read race, a one-click approval is applied to the extension's original multi-item targets because no request context is compared.

Bind approval to exactly what the host parsed and presented. A response can include a host-computed digest of the canonical request bytes that the extension compares with its original, or the host can receive the request over a bidirectional socket after the extension authenticates the peer; the latter makes DNC strictly wake-only.

### The confirmation lifetime splits into 60 seconds, launch time, and 120 seconds

**confirmed:** the shared protocol declares 120 seconds (`Shared/MenuAction.swift:1081-1083`), but `readRequest` rejects requests older than 60 seconds (`Shared/MenuAction.swift:1119-1128`). The extension stamps `createdAt`, writes the request, and awaits `NSWorkspace.openApplication` with an unchecked continuation (`FinderExtension/FeatureServices.swift:1138-1157`, `FinderExtension/FeatureServices.swift:1192-1216`). Only afterward does it create a new 120-second sleep (`FinderExtension/FeatureServices.swift:1158-1189`).

The host derives the modal timer and final approval check from `createdAt` (`App/SuperRightClickApp.swift:114-165`), but the extension does not. A launch delayed beyond 60 seconds is rejected by the host while the extension can wait another 120 seconds; launch itself has no bound. A response queued on the listening socket can also be accepted after `createdAt + 120 seconds` if launch completion arrives late, because the extension never checks request age before acceptance.

Compute one expiration instant from `createdAt + 120 seconds` and apply it to intake, launch, modal presentation, socket receive, and queue cleanup. Start timeout enforcement before awaiting Launch Services and reject every response after that absolute deadline.

### Blocking connect can hold the serialized modal queue indefinitely

**confirmed:** `LocalUnixSocket.send` creates a blocking socket, sets `SO_NOSIGPIPE`, and calls `connect()` before applying `O_NONBLOCK` (`Shared/MenuAction.swift:981-1009`). Nonblocking mode is set only in `waitForPeerClosure`, after write and `shutdown(SHUT_WR)` (`Shared/MenuAction.swift:1010-1040`). A blocking Unix-domain `connect()` can wait when the finite listener backlog is full; this listener uses backlog 4 (`FinderExtension/FeatureServices.swift:96-98`), and same-user processes can learn its path from the request.

The host awaits that detached send before clearing `destructiveConfirmationTask` and processing the next request (`App/SuperRightClickApp.swift:86-112`). The two-second peer-closure deadline therefore does not bound the handshake, and backlog saturation can leave a dismissed request occupying the queue. Configure nonblocking mode before connect, poll `EINPROGRESS`, and keep connect, write, half-close, and peer-close under one deadline while retaining `SO_NOSIGPIPE`.

### Boundary coverage does not exercise the remaining failure modes

**confirmed:** all 33 Debug tests pass, but `testAuthenticatedConfirmationReplyChannel` covers only same-process hash acceptance and an all-zero expected hash (`Tests/CoreTests.swift:218-253`). The request test treats 61 seconds as stale (`Tests/CoreTests.swift:183-215`), cementing the 60/120 mismatch. Deletion tests cover default denial and stable disabled preference (`Tests/CoreTests.swift:709-747`), while safety-file tests cover malformed data, symlinks, and unknown schemas (`Tests/CoreTests.swift:127-180`).

Not tested: request substitution with unchanged ID/socket, response-context binding, delayed or never-completing host launch, backlog-saturated connect, invalidation during accept/read, approval at the absolute deadline, and queue progress after an expired response send. Add short-deadline seams and socket-level tests for these boundaries, plus a host/extension test proving that the modal context is the context authenticated by the extension.
