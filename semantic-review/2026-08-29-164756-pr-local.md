# Permanent deletion foreground confirmation with opt-out safety gate

This change moves permanent-delete confirmation from the Finder extension into the foreground host app, keeps `confirmBeforePermanentDelete` in a separate hardened preferences file, and binds execution to the Finder URLs captured when the menu was built. The storage path fails closed and direct deletion requires two reads of the same `false` revision, while confirmed deletion rechecks path, device, and inode before removal. The cross-process approval path is not yet safe enough to ship because approval is unauthenticated, a host-startup window can lose requests, and the host modal can outlive the extension's timeout and block the serialized queue. **Watch for:** **confirmed** forged distributed responses can bypass confirmation; **likely** requests issued while the host is starting can be dropped; **confirmed** a timed-out request can leave a stale modal blocking later confirmations; **confirmed** tests do not exercise these process-boundary paths.

**Verdict**: NEEDS_CHANGES

## High-level view

`SafetyPreferences.json` is independent of `MenuConfiguration`. The host settings model is the only production writer, each save creates a new revision, and the extension validates the file at operation time. Missing, malformed, incorrectly permissioned, linked, oversized, raced, or unknown-schema data resolves to confirmation; a stable disabled setting must be observed twice before bypassing the host.

The extension writes a private request file, registers its response observer, then notifies or launches the host. The host validates and deduplicates requests, serializes foreground alerts, and posts a UUID-matched response. The UUID separates concurrent requests but cannot authenticate the sender because it is exposed in the distributed request notification.

Finder commands retain the URLs and target directory from menu construction. The extension—not the host—keeps the actual targets and revalidates path, resolved path, device, and inode before removal; `requiresConfirmation=false` is confined to tests.

The lifecycle handoff has two availability gaps. A process counted as running can still be earlier than observer registration, while the extension sends only two ephemeral notifications 150 ms apart; once an alert is shown, the extension's 120-second deadline does not dismiss it or release the host's serial queue.

1. **Unauthenticated DNC approval** — **confirmed:** the exposed request UUID is the only approval check, so another process can forge `approved=true`; move approval to authenticated IPC or require an authenticated response.
2. **Warm-start request loss** — **likely:** two notifications within 150 ms can both precede host observer registration; add durable startup pickup or retry until an explicit receipt acknowledgment.
3. **Expired modal blocks the queue** — **confirmed:** the extension times out after 120 seconds but the host alert stays modal and serializes later requests behind it; enforce the same absolute deadline in the host and auto-dismiss expired work.
4. **No process-boundary regression coverage** — **confirmed:** current tests use an in-process confirmation stub and cannot expose forged responses, startup loss, or stale modal queues; add host/extension integration tests for those paths.

<summary>Details</summary>

### Distributed notifications cannot authenticate approval

**confirmed:** the request UUID is embedded in the request filename (`Shared/MenuAction.swift:976-999`) and the complete path is broadcast through Distributed Notification Center (`Shared/MenuAction.swift:1036-1042`). Responses use the same unauthenticated channel (`Shared/MenuAction.swift:1059-1084`), and the extension accepts `approved=true` based only on equality with that exposed UUID (`FinderExtension/FeatureServices.swift:872-875`). Another process in the user's distributed-notification domain can observe the request and immediately publish a matching approval, bypassing the foreground decision and causing deletion of the still-matching captured target.

The `0600` request file protects its contents but does not make the disclosed UUID a capability. Move approval onto authenticated IPC, such as XPC with peer code-signature/audit-token validation, or require a cryptographically authenticated response whose key is never published through DNC. DNC can remain an untrusted wake-up hint.

### Warm-start signaling has an observer-registration blind window

**likely:** when `runningApplications(withBundleIdentifier:)` reports the host as present, the extension posts immediately, sleeps 150 ms, posts once more, and then waits (`FinderExtension/FeatureServices.swift:903-915`). A newly launched process can be visible to Launch Services before `AppLifecycleModel` installs `observeRequests`, so both notifications can precede registration. The cold branch protects its first request with a launch argument, but a second delete during that startup takes the running-host branch without a durable recovery path.

This produces a silent 120-second wait and cancellation even though the host launched. Persist an inbox that the host scans at startup, or retry until the host acknowledges receipt while the request remains valid; two fixed-delay posts are not a readiness protocol.

### The extension timeout does not expire the host modal queue

**confirmed:** the extension races the response stream against a 120-second sleep (`FinderExtension/FeatureServices.swift:884-900`), while the host uses an unbounded `alert.runModal()` and keeps `destructiveConfirmationTask` non-nil until it returns (`App/SuperRightClickApp.swift:82-129`). If the alert stays open past 120 seconds, the extension returns `false` and removes its observer, but the stale modal remains. A later approval is ignored, and subsequent confirmations stay queued until the modal is manually dismissed.

Concurrent requests start their extension-side timeouts before the serial host queue presents them. A request can spend most or all of its lifetime behind another alert and then appear with no useful response window or expire without presentation. Give host presentation the same absolute deadline, automatically abort the modal at expiry or requester cancellation, and discard expired queued work before presenting it.

### Process-boundary failures are absent from the test suite

**confirmed:** the tests validate basic secure-file behavior and route deletion through an in-process confirmation closure (`Tests/CoreTests.swift:113-215`, `Tests/CoreTests.swift:668-706`). They do not run a host/extension pair, delay host observer registration, overlap requests, cross the modal deadline, or attempt a forged distributed response, so the three blocking behaviors above remain invisible despite the passing Debug suite.

Add integration coverage for delayed warm startup with a second request, rejection of unauthenticated responses, concurrent serial confirmations, and automatic cleanup at the 120-second deadline. Retain the local fail-closed and stable-revision tests for the storage gate.
